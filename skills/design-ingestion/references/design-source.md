# Design source — where the values come from

Something arrives before the markup: a design file, an export, a screenshot, a brief. The router
ranks them and says which wins. **What none of them says is how to get the values out of the
winner, or how to tell what the winner actually is.** That is this file.

Hand it to whatever is about to turn a design into a page.

## Start here

**Section 0 is the one to read.** The rest is a list of what to extract and it is unsurprising.
Section 0 is the part that is wrong in most projects, and wrong silently: a file that opens in a
design tool is not automatically an authored design, and if it is not, it does not get a designer's
authority over your values.

**Nothing here decides which input wins** — the router owns precedence and this file feeds it. What
it adds is the question precedence cannot be answered without.

## 0. Provenance, before precedence

**Ask, before ranking anything: who authored this, and what generated it.**

A design file gets its authority from somebody having made decisions in it. Not from having layers,
not from having variables, not from having components — those are structure, and structure is
exactly what a generator produces. **Rank by provenance, not by format.**

| What you have | Trust it for | Do not trust it for |
|---|---|---|
| **Authored** — somebody made the decisions in it | exact values: colour, type scale, spacing, states, component boundaries | anything it does not contain. A state it never drew is not a decision it made |
| **Generated, then imported** — produced by a component library or a template and opened in a design tool without being touched | what the result should look like, the section inventory, the section order, the copy | any value, because nobody chose one. Its variables are the library's defaults |
| **Generated, then edited** | the edited parts, as authored | the untouched parts, which are still defaults nobody chose |
| **An exported or scraped page** | what the result should look like, and the copy | its markup or its class names, ever |
| **A flat image** — screenshot, JPG, PDF | proportion, hierarchy, mood | any number read off it, all measured from a render at an unknown zoom |
| **The live page** | what is shipped today | what was intended, and whether it is current with anything |

**The row that costs money is the second one**, because it is indistinguishable from the first at a
glance and it is common. A file generated by a component library and imported into a design tool
has real layers, real variables, real components and real auto-layout. It passes every test anyone
applies before deciding to trust it — and the values in it were chosen by a library, in a vacuum,
for nobody's brand.

### How to tell

None of these is proof on its own. Two of them together is enough to ask.

- **Layer names follow a convention rather than a project.** Systematic, uniform, and the same in
  every frame.
- **Variables nobody renamed.** A palette of generic names, a spacing scale in round numbers, and
  no name that refers to anything about this client.
- **Components are library instances with no overrides.** Nothing has been pushed away from the
  default.
- **Section structures repeat exactly across frames**, including the parts that would not naturally
  be identical.
- **The file is far larger than the project** — dozens of unused components and styles nobody
  brought in on purpose.

**And then ask.** It is one question, it costs nothing, and it changes the rank of your
highest-ranked input. "Was this drawn, or generated and imported?" is a question anybody with the
file can answer in a second and nobody can answer from the file alone with certainty.

### Do not assume the design file is the final truth

When there is a chain — a generator, then a design tool, then code — **which one is live is a fact
about the project, not something to deduce.** Get it stated:

- if the site ships from somewhere else, the design file may be a snapshot of a decision that has
  since moved, and matching it faithfully reproduces the past;
- if the design file was edited after being imported, **the edits are the decisions and the
  untouched parts are defaults nobody chose** — those two halves have different authority and they
  sit in the same file;
- if nothing was edited, the design file adds no authority over the generator's own output. It is
  the same content in a different container.

**If nobody says which one is authoritative, stop and ask.** That is the one question worth
interrupting for: both answers are defensible, only one is what they wanted, and the cost of
guessing is not a wrong pixel — it is a whole batch built against a stale reference and passing
every check.

**Whichever you rank first, write it down with its reason**, beside the project's other settled
decisions. Six weeks later, "we decided the design file wins" and "nobody asked" are
indistinguishable, and only one of them is a decision.

## 1. What to extract, and in what order

One node, one pass, before any markup. The order is cheapest-first: each of these makes the next
one shorter, and doing them the other way round means measuring things you were about to replace.

1. **Frame identity** — its name, and its exact width and height. The width is what every later
   comparison is made at, so an approximate one poisons everything downstream.
2. **Variables and styles** — the palette, the type scale, the spacing scale, as the file defines
   them rather than as they appear on any one element. This is the difference between reading a
   system and reading one instance of it.
3. **Typography, completely** — family, weight, size, line-height, letter-spacing. Line-height is
   the one that gets dropped and it is the one that changes where text wraps.
4. **Geometry** — widths, heights, padding, margins, gaps, border radii, borders.
5. **Colour**, including the ones you would not think to ask for: borders, dividers, the state
   variants.
6. **The asset inventory** — every image and every icon, listed before any is exported, so the
   count is known and a missing one is visible.

**Take these from the node itself, not from a code panel.** A design tool's generated code is
covered by section 3 and it is not a source.

## 2. Assets are exported, never approximated

**This is the single most common defect in design-to-code work and it survives every automated
check that exists.**

Icons come out as an emoji, a Unicode character, a similar icon from whatever icon library the
project already has, a generic SVG, or a placeholder that nobody went back for. Each of those
renders. Each passes a type check, a build, a lint, an accessibility audit and a Lighthouse run.
Each is visibly wrong to the client, in the first ten seconds, on the first page.

**The rule: every icon and image comes from the design's own asset, exported.** Not something that
looks like it. Not the closest match in a library the project already installs.

Two consequences worth stating because they are where this gets abandoned:

- **A missing asset is a blocker, not a licence to substitute.** If the file will not give it to
  you, say so and stop, rather than shipping a lookalike that nobody will ever know to check. A
  named gap is cheap; an unnamed substitution is found by the client.
- **An icon library is not a fallback.** It is a different set of drawings with a different weight,
  a different corner radius and a different optical size. "Close enough" here is the judgement that
  produces a page that is subtly wrong everywhere and traceable nowhere. Installing a new icon
  package to fill a gap in the export is the same substitution with a dependency added to it.

**A URL to an asset is not the asset.** A server that hands you assets over a link hands you a
temporary one — Figma's expire in about a week — so a project that keeps the link ships a page
whose icons work in review and are gone a sprint later. Download the bytes into the repository and
reference the file. This is the one defect in this section that passes even a visual check, because
it passes on the day you look.

**Two dimensions, not one.** An exported asset has an outer box and a drawing inside it, and they
are separate facts: the padding between them is a design decision the export carries. Give the
container both a width and a height and let the image fill it. Sizing by one axis, or leaving it to
the intrinsic size, renders the drawing at whatever scale it happened to be exported at — and one
size applied across unlike assets is the same error committed everywhere at once.

**Check them the way section 4 of [visual-fidelity.md](../../visual-gate/references/visual-fidelity.md) checks them** — against the reference image,
not against your memory of what the icon looked like.

## 3. Generated code is an export

A design tool that hands you code, and a component library that generates a page, are both giving
you an **export**: a render of a decision, produced by a tool optimising for something other than
being read.

- **Values from it are as good as their provenance** — which section 0 already settled, and no
  better because the values arrived as code rather than as a panel.
- **Structure from it is never used.** Copying the markup imports a dead end that looks like a head
  start: nesting that exists to satisfy the generator, class names that mean nothing in your
  project, and a shape nobody on the team can extend. Structure comes from the structure contract
  for the stack you are on, whatever the input looked like.

**This is the rule that is hardest to keep**, and the reason is worth naming: a good component
library produces structure that looks good. The output is not obviously bad, which is exactly what
makes copying it tempting, and the cost arrives four pages later when the fifth page needs
something the generated shape cannot express.

## 4. Reading a design tool over an MCP server

Named because it is now the common way this work arrives, and because what each call returns
changes what you may conclude from it.

**The vendor owns the call sequence, and ships it as a skill.** Figma's MCP server publishes
`figma-design-to-code` and declares it a prerequisite of its own context call: it names which call
to make first, the order in which to resolve the hints that come back, and what to do when a
response is truncated. Read it from the server. A call sequence copied into this file would be a
second copy of somebody else's contract, and the copy that goes stale is always the one in the
document that does not own the subject — the tool names have already rotated once.

**It is an aid, not a step.** Not every editor has that server connected, a file can be view-only,
and a document that assumes one fails silently everywhere it is absent. Nothing below depends on
it: all of it stays true when the design arrives as a file, a link or an export.

What this document owns is the second column — what each kind of response is *worth*.

| What you asked for | What you got | What it is worth |
|---|---|---|
| Design context for a node | its structure, its styles, and often generated code | values, subject to section 0. **The code half is an export** — section 3 |
| A screenshot of the frame | an image | **a flat image.** It is a render at a scale you did not choose. It is the reference for comparison and it is not a source of numbers |
| Variable definitions | the file's tokens | the system, which is better than reading values off one element |
| Assets | files | the only acceptable source for icons and images — section 2 |
| Metadata | names, ids, dimensions | the frame identity that every later comparison is anchored to |

**The screenshot row is the one that gets misread.** It arrives from the same place as everything
else in the same breath, so it inherits the authority of the design file in the reader's head. It
should not: it is a picture, it falls in the flat-image row of section 0, and a number measured off
it is a number measured off a render.

**Work one node at a time.** Two nodes in the same pass produce values that get attributed to the
wrong one, and the error is invisible because both sets of values are plausible.

### Four failures that end in a defended wrong value

The vendor's skill covers its own mechanics. These four are this document's business, because each
one produces a complete, plausible extraction of something nobody asked for:

- **A file-level link is not a node.** A link with no node identifier names a document, not a
  frame. Ask for a node-specific one rather than guessing which frame was meant. A guessed frame
  extracts cleanly and answers the wrong question, and section 6 will record it as though it were
  the right one.
- **A truncated response is a scoping problem, not a retry.** Re-issuing the same call returns the
  same truncation. Ask for the node's own map, pick the children you actually need, and fetch only
  those. Raising a limit is not available to you and would not help.
- **A response that will not narrow means the node is too large.** Retry against a smaller
  selection. No size at which this starts is published, so it is a symptom to recognise rather
  than a threshold to calculate — which also means "the node was too big" is never an explanation
  you can check afterwards, only one you can act on now.
- **Record the node identifier verbatim**, in whatever form you were given it. It is the anchor
  section 6 asks for, and a re-typed identifier is the one detail nobody re-verifies.

## 5. What a design file does not contain

Everything below is absent from most design files, and its absence is not a decision — it is a
question nobody was asked.

- hover, focus and active states;
- error, empty and loading states;
- what happens at widths the file was not drawn at;
- what happens to text longer than the text that was drawn;
- what happens when an image is missing;
- **a licence for the typeface it names.**

**That last one is not like the others, and it is the one that ships wrong.** A design tool renders
a font because the machine that opened the file has it; it does not substitute silently, it asks a
person, and that person's answer is not recorded in the file. So a family name in a design is
evidence that somebody chose it and no evidence at all that the project may serve it. Until a web
font file is in the repository, the name is a request.

Two ways this goes wrong, and neither announces itself:

- **Substituting a lookalike.** The page builds, renders, and reads as finished. Wrong type at the
  right size is the defect a client sees immediately and a review never does.
- **Reaching for the one whose name resolves cleanly.** A default sans is the tempting answer
  precisely because it is always available. A design naming something the project does not have is
  a question for whoever commissioned it, not a gap to close with the nearest font that loads.

Where a font that never loaded is *caught* is a different job: [visual-fidelity.md](../../visual-gate/references/visual-fidelity.md) §3.2 owns it,
and explains why the browser reports success either way.

**Fill them in. That is your job and it is fine.** What is not fine is filling them in silently:
every one of these is a guess, and a guess that is never labelled becomes a fact the next person
inherits without knowing anyone chose it.

**Say what you inferred, in the handover**, not only in a file at the root. A decision recorded
where nobody looks is a decision the client learns about by using the site.

## 6. Recording the extraction

Write down what you took, once, where the next person will find it. Not to be tidy — because the
alternative is paying for the whole extraction again, and because a value with no recorded source
cannot be defended when somebody asks why it is 34 pixels.

At minimum: which node, which frame, its width, the provenance you established in section 0 and how
you established it, which input you ranked first, the assets you exported and the ones you could
not get.

**When the site is a batch of many pages, this belongs in its manifest** rather than in a file per
page — the batch's own document owns those fields. When it is one page, a section in the project's
design notes is enough.

### The record is the source after the first pass

Once written, that file is what every later pass reads. **The design is consulted once per node,
not once per component.**

This is the difference between an extraction and a habit of asking. A build that re-reads the
design for each section pays for the same values repeatedly, and pays in the one currency that runs
out: a design response is among the largest things that will enter the work, and a second one for
values already recorded buys nothing but the risk of transcribing them differently the second time.
Two passes that disagree about a spacing value produce a page that is subtly inconsistent and a
record that matches neither.

So the order is: extract, write it down, then build from what you wrote. Go back to the design for
something genuinely absent from the record — a state nobody extracted, a node not covered yet — and
when you do, add it to the record rather than using it and moving on. **A value used but never
recorded is the one nobody can defend later**, which is the whole reason this section exists.

## 7. What this document cannot do

- **It cannot establish provenance for you.** Section 0 lists signals and none of them is proof.
  The reliable move is asking, and this document can only tell you that it is worth asking.
- **It cannot tell you the design is good**, or that the node you were pointed at is the right one.
- **It does not decide precedence.** It supplies the question precedence depends on; the router
  ranks the inputs and says so out loud.
- **It cannot see that an exported asset is the wrong asset.** Comparing what you built against the
  reference is a different job, and [visual-fidelity.md](../../visual-gate/references/visual-fidelity.md) owns it.
- **Nothing here is checked by any tool.** Every rule in this file is read-and-apply, and a
  completed extraction is a claim by whoever made it.
